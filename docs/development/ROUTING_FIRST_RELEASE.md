# Routing-first OCP delivery

2026-11-02. Local delivery decision and agent rehearsal; not a publication record.

The user selected a routing-solver connection as the first delivery. OCP remains
a host-independent optimization interface. The first no-key implementation is
OR-Tools through `routing.basic@0.1.0`, with explicit meter matrices, integer kg
capacities, a single depot and mandatory visits. This decision does not narrow
the common contract or remove worker, inventory or installed extensions.

## First delivery

- Local stdio MCP with `--domain routing-basic --evidence`.
- One routing catalog, eleven tools, independent verification and checked
  explanation facts. Discovery is useful without executing the solver.
- Installation, diagnosis, generated host configuration and a routing quickstart
  shipped together. The generic multi-domain command stays compatible.
- An ordinary external application supplies the matrix. Address lookup, road
  travel-time generation and time-window optimization are separate capabilities.

The current bundle still contains the multi-domain implementation and examples;
the first connection configuration exposes only routing. This is not a new
protocol version, a stripped-down wheel or a hosted endpoint. Source package,
native contract, profile and optional evidence versions remain distinct.

## Rehearsal and interpretation

Use a new extraction and virtual environment for the public ZIP, then a separate
environment for the candidate. Use only the delivered package while executing;
do not import source checkouts. Keep public and candidate results separate.

Exercise discovery, a four-visit route, a capacity-change comparison, missing
matrix data, unsupported time windows, wrong units, provable capacity
infeasibility, repeated submission and deliberately corrupted results. Check
route loads, distances and visit coverage independently of the solver. Run the
same fixtures on macOS arm64 and Linux amd64 (Docker emulation is labelled).

Also record a direct interaction through the MCP connection in the current
Codex host, identifying its advertised version. That existing connection is not
automatically upgraded by building a candidate. Scripted protocol tests are
separate from model conversations.

The implementing agent has prior project knowledge. This is an assisted
first-user rehearsal, not a blind test, external participant or adoption study.
Record blockers and interventions; do not infer user satisfaction or installation
time for an unfamiliar person from command execution time.

## Release acceptance

1. The exact selected artifact installs and solves on the declared platforms;
   selected-domain discovery and rejection agree with configuration.
2. Required data and constraints are preserved. Invalid input is rejected before
   execution; unknown and infeasible remain distinct; supplied results are checked.
3. Runtime contents and test sources are pinned. Public-file selection, notices,
   dependency versions and current release-gate evidence are reviewed together.
4. The public package, README and website point to the same released candidate.
   Registry names and the immutable release tag must be resolved before publishing.

The last two items are publication preparation, not satisfied merely by local
tests. The source changes and exact posting targets are presented for review
before a new main push, release asset, registry or Pages deployment.

## Next evidence

First complete routing connection for a second target host using its supported
transport, then observe an outside developer and a conversation user with a
task they actually need. Remote operation needs a chosen HTTPS environment,
authentication, user-specific job isolation, retention/recovery and cost limits.
Use those results to choose the next routing capability or adapter. Require a
real user's need before expanding profiles solely to enlarge a feature list.

The separately approved 0.3.0/0.4.0 comparison has now completed all 48
synthetic Claude Code/Sonnet sessions. Structured checks passed 24/24 per arm;
strict final-answer review passed 22/24 and 23/24 respectively. Both miss the
24/24 explanation target. A changed suggested start time in 0.4.0 reinforces
the need to compare host-proposed alternatives with original requirements.
This is not a 0.5.0 candidate host trial or an external-human acceptance result.
