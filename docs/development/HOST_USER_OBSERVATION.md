# First-user observation packet

Status: prepared locally, participants not yet recruited, no user result recorded.
Use OCP as a host-independent optimization interface. Invite one developer
using an MCP development host and one person using an MCP conversation host.
Record the exact application, version, model, transport and installed candidate.

## Before the session

Ask the participant for one bounded optimization question they actually need
answered and a synthetic or de-identified input they can share. Record the desired
outcome and mandatory rules before selecting a supported profile. If the profile
cannot represent the task, record that fit gap and the required capability.
Do not change mandatory requirements just to complete the demonstration.

Provide the current installation/connection guide and candidate. Keep reviewer
answers separate. Give assistance only when requested or when the session is
stuck; log each intervention rather than counting assisted completion as unaided.
Do not contact or send this packet to anyone without the user's send instruction.

## Developer task

Connect the server to the chosen host. Discover domains and required data, ask a
context-only question, then use the request/result flow in a small existing or
throwaway application. Show how the application handles missing input, unsupported
requirements, pending jobs and independently checked results.

## Conversation task

Connect the server, ask what it can solve, supply the chosen data, resolve missing
information and obtain a solution with its limits explained. If comparing options,
use two supported problem scenarios and inspect both checked results. Ask the user
to explain what was optimized and what was not covered, in their own words.

## Record each session

| Field | Record |
| --- | --- |
| Participant type and task | Developer / conversation user; original intended outcome |
| Environment | Host, model, OS, transport, candidate manifest and feature version |
| Fit | Required rules supported / missing capability; no guessed requirements |
| First connection | Elapsed minutes, failed steps and assistance |
| First useful result | Elapsed minutes, original task achieved / partly / not achieved |
| Correctness | Exact input, mandatory rules, independent checker scope, final explanation issues |
| Assistance | Every intervention and whether completion depended on it |
| Usefulness | What would they use next week? Would they reuse it? Why or why not? |
| Follow-up | One highest-priority blocker or capability request |

Keep identifying information and source data private. Publish only an explicitly
approved summary. A useful result, an unaided first connection and an understood
verification boundary are separate observations; two sessions are diagnostic,
not an adoption-rate estimate. The output is a short decision record connecting
observed barriers to the next implementation priority.
