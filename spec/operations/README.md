# Optional operations — private implementation candidate

Status: private continuation `ocp.operations` `0.1.0-draft.2`, accepting the unchanged draft.1 shape. This is not adopted public normative text. Core, native wire and existing single optimization API contracts retain their meanings. The extension lives in the existing `extensions` object. Packages that need it include its ID in `required_extensions`; a consumer without support must reject before effects. Unknown optional extensions remain opaque.

Each operation declares ID/version, kind (`query`, `command`, `optimization`), local request/response schema names, description, effects, execution mode and binding. Optional `context_schema` describes a separately supplied non-null optimization context. It does not establish identity or permission. The installed deployment policy authorizes the transport-provided principal against context/request before invocation. No tenant, ward, project or UI field is a universal requirement.

Query and command use installed `OperationConnector` entries selected by opaque connector IDs. Metadata may not name an import or URL. The entire descriptor, referenced schemas and operation form the exact discovery/invocation reference. The live connector must describe the exact operation on discovery and before invocation. Query declares `none`; command declares `optimization_context_write`. Connectors return `OperationAnswer(data, effect)` with actual effect `none`, `applied`, `partial` or `unknown` as permitted. Reported data must match the exact response schema. Queries cannot report write effects. Registered connectors remain trusted code; declarations are not a process sandbox or proof that arbitrary connector code cannot lie.

Processing results use `completed`, `partial`, `failed`, `uncertain`, retaining original request ID and data/null. They do not use feasible/optimal/infeasible. Command response or validation failure after invocation is uncertain, because effects may already have occurred. A durable SQLite reservation scoped by trusted tenant and caller precedes invocation; duplicate request IDs return the known observation or pending uncertainty without invoking again. A conflicting request is rejected. No automatic retry occurs, including restart and lost journal acknowledgement. This is a single-host observation journal, not upstream idempotency, reconciliation or an atomic context transaction. Those capabilities, and cancel/snapshot, are explicitly false in this first candidate.

Optimization operations reference the existing API ID/version and its input/result schemas. They accept the existing configuration separately and reuse ExecutionService validation/outcome/checker behavior. Their context must be materialized into API input before this bridge. The MCP binding keeps `ocp_submit/job/result/evaluate/cancel`; it does not expose a synchronous optimization shortcut as a new tool.

The MCP binding adds a separate fixed tool for each registered query/command. Query has read-only annotation; command has conservative destructive annotation and no idempotency hint. There is no arbitrary `call_tool` proxy. Exact schemas and references are available through paged `ocp_describe` sections `operations` and `operation_schemas`; MCP request wrappers carry those references. Stdio and HTTP obtain principals from their existing trusted binding. A payload cannot supply a principal.

Consumers with older input-only tools can keep those bindings. An adapter must preserve their actual result envelope and use an identified source contract when output metadata is absent. This generic candidate does not invent an envelope for legacy responses.

This generic package does not supply customer-specific state materialization, deployment authentication or production domain connectors. Those belong to separately configured adapters and application acceptance.

TypeScript SDK validation uses the same canonical operations JSON Schema as an explicit trusted fifth `lintPackage` argument; the schema is not accepted from tool payloads. `operationReference` uses the same existing fingerprint namespace as Python. The TypeScript candidate does not provide a second dispatcher/runtime implementation.

## Optional file preparation — draft.2 private continuation

The independent preparation candidate adds `0.1.0-draft.2` and accepts the unchanged draft.1 shape. Only draft.2 may declare `input_formats` inside an operation. These are local official format definitions using the same format/table/column schemas as legacy preparation, checked for exact parity. The existing top-level `input_formats` and `prepare()` continue to target the original optimization API. A missing operation format never falls back to a legacy format or another operation.

`ocp_runtime.inputs.prepare_operation(descriptor, operation_id, payload, expected=reference, context=..., format_id=..., format_version=..., converters=...)` accepts direct JSON or supplied CSV/XLSX bytes and returns a `prepared_operation_request`. It checks the exact operation/package reference and context, performs shared file parsing, validates the operation request schema, and preserves file hashes, cell provenance and registered converter derivations. Commands and queries do not use the legacy optimization input schema. Optimization preparations retain the existing configuration validation.

Preparation exposes no dispatcher, job, database or execution port. It returns `status=prepared`, `effects=none`, `execute_calls=0`, and `authorization=not_evaluated`; none of those fields establish permission to invoke. The installed converter is still trusted transformation code and cannot be made pure by a metadata declaration alone. The subsequent operation invocation independently rechecks reference/schema/context/transport authorization. The existing `ocp_prepare` tool remains the legacy API preparation tool. The separate MCP preparation continuation adds `ocp_prepare_operation` only when an installed operation service is registered; live Studio integration remains separate work.

## MCP preparation continuation

`ocp_prepare_operation` is a read-only tool using the transport read scope. Read the exact operation reference, format and schemas through `ocp_describe`; upload files through `ocp_artifact`, then pass their complete owner-scoped references. Direct JSON uses `request_value`. The reference and installed connector authority are checked before reading artifacts. Paths, URLs, raw base64 and caller-provided schemas are not file inputs. Preparation never calls the operation authorization/invocation callback or solver; the later explicit invocation performs its own authorization. `authorization=not_evaluated` specifically means operation execution authorization. Large preparation results use the existing owner-scoped artifact mechanism. The original legacy tool set is unchanged when no operation service is registered.

## Optional synchronous completion observation (private runtime continuation)

Runtime `0.4.0.dev10+publicformat1` adds `OperationAnswer(..., completion="acknowledged")`. This opt-in connector observation means the synchronous provider operation completed according to its contract. It is not asynchronous job acceptance, mathematical feasibility, or a receipt proving a write. A validated response with unknown mutation effects may produce `status: completed`, `effect: unknown`, `completion: acknowledged`. A partial effect remains partial. Null data is allowed only when the response schema allows it and never implies completion.

Legacy connectors omit completion and retain the exact previous report shape and status rules. The declaration schema and extension version remain unchanged; the result contract has an optional additive property. Connectors opting in must pin a runtime supporting this API and version their operation reference. Closed report consumers must admit the new optional property before selecting that operation version. All three operations classes (service, connector, answer) must come from `ocp_runtime.operations`; mixing private prototype namespaces is rejected.

Malformed responses, transport loss, unresolved reservations, and lost durable journal acknowledgement preserve uncertainty without a completion claim or automatic resubmission. Existing uncertain journal rows are replayed unchanged. Authorization is checked again before replay. Native optimization job submission/polling and result semantics are unchanged. This is a private implementation candidate, not a change to published Core or native wire standards.
