먼저 로컬 실행을 완료하고 생성된 kit 폴더에서 진행하세요. 지원 기능 조회 → 요구사항 확인 → 검증 → 실행 → 반환된 해 평가 → 독립 검산 순입니다. OCP는 특정 UI 프레임워크나 Omelet 계정을 요구하지 않습니다.

Python

.agent/bin/python -I -B multi_app.py --profile routing.basic --input basic-input.json --request-id first-routing
.agent/bin/python -I -B multi_app.py --profile worker.scheduling --input worker-input.json --request-id first-worker
.agent/bin/python -I -B multi_app.py --profile inventory.replenishment --input inventory-input.json --request-id first-inventory

파일 multi_app.py 을 열어 입력·표현 코드를 내 앱에 맞게 바꾸세요.

Node / TypeScript

Python 환경은 loopback 참조 제공자를 실행하고 Node 클라이언트는 내 앱에서 실행합니다. Node 의존성 설치와 제공자·클라이언트 별도 터미널 안내.

MCP: 계산 전에 컨텍스트 제공

요청 예시: “차량 용량을 지키면서 배송 거리를 줄여줘.”

  1. 컨텍스트를 조회합니다. 먼저 ocp_context()를 호출하고, 공개된 프로파일을 선택한 뒤 입력 스키마와 요청 템플릿을 확인합니다.
  2. 빠진 데이터를 확인합니다. 차량 용량이나 누락된 거리를 질문합니다. 값을 지어내거나 제약을 조용히 빼지 않습니다.
  3. 검증한 뒤 실행합니다. 지원하지 않는 요구사항은 계산 호출 전에 거절합니다.
  4. 평가하고 설명합니다. 반환된 해를 평가하고 별도 checker를 실행해 실제 상태·비용·검증 범위를 보고합니다. 알 수 없거나 평가하지 않은 값은 그대로 유지합니다.

OCP는 최적화 요청과 결과의 의미를 정의합니다. 선택적인 MCP binding은 이 컨텍스트와 연산을 AI 호스트에 전달합니다. Python·HTTP 앱은 MCP 없이도 OCP를 사용할 수 있습니다.

이 흐름은 권장 사용법이며 실제 모델 대화 기록이 아닙니다. 로컬 서버와 smoke 검사는 모든 모델·호스트의 올바른 동작을 입증하지 않습니다. 제공자의 평가와 독립 검산은 별도 단계입니다.

로컬 MCP 서버 검사·설정
.agent/bin/python -I -B local_agent.py doctor --profile all
.agent/bin/python -I -B local_agent.py smoke --input basic-input.json --request-id first-mcp
.agent/bin/python -I -B local_agent.py config --profile all --format json
.agent/bin/python -I -B local_agent.py config --profile all --format codex

Doctor는 계산 호출 없이 도구 6개와 세 프로파일의 컨텍스트를 검사합니다. Smoke는 실제 라우팅 문제 하나를 계산하고 비용 18을 독립 검산합니다. Config는 절대 경로를 포함한 JSON 또는 Codex TOML을 출력하며 호스트 설정을 직접 바꾸지 않습니다. MCP 호스트가 실행되는 컴퓨터에 설치하고, 출력을 검토해 해당 호스트에 추가한 뒤 MCP 설정을 다시 불러오세요.

에이전트는 ocp_context()로 시작하세요. 입력 스키마와 요청 템플릿을 확인하고 빠진 값을 질문한 뒤 실행 전에 검증합니다. feasible과 optimal, timeout과 infeasible, null과 0을 구분하세요. 이 로컬 명령은 모델을 호출하지 않습니다. 호스트·모델 사용에는 별도 한도와 비용이 적용됩니다. 호스트 설정·문제 해결 안내.

무엇을 검증했는지 명시하세요

기존 측정치 옆의 verification 보고서를 확인하세요. 실행 가능성·비용 재계산·최적성·불가능성은 별도 상태입니다. PARTIAL이나 INCOMPLETE는 검사하지 않은 증명을 입증하지 않습니다. 오프라인 검산은 엔진의 실제 실행을 증명할 수 없습니다.

검증 항목·한계·독립 CLI.

Native v1: 별도 앱·MCP binding

이 소스 프리뷰는 다음 안내로 빌드하세요: native 설치 안내. 위의 Core 설치와 도구 6개는 별도 경로입니다. Native Python import: NativeClient 을 ocp_candidate.native; Node import: createOptimizationApiClient 을 ocp-candidate/native. 기존 루트 import는 Core 0.1을 유지합니다.

후보 MCP 진입점은 ocp_runtime.native_mcp입니다. 도구 8개는 실제 작업과 명시적 도메인 선택을 사용합니다. 시작 도구는 ocp_native_context입니다. 공개된 템플릿인 selectionTemplate 및 requestTemplate을 사용하고, 빠진 데이터를 질문하세요. payload를 지어내지 마세요.

Native 후보 도구 — native 소스 설치 경로에서 제공
도구역할
ocp_native_context도메인 목록 또는 선택한 카탈로그·스키마·템플릿을 조회합니다.
ocp_native_requirements계산 없이 설정·입력 요구사항을 확인합니다.
ocp_native_validate선언된 문제 본문을 검증합니다. 잘못된 입력은 불가능 판정이 아닙니다.
ocp_native_submit명시적인 멱등 키로 실제 작업을 제출하고 작업 정보를 반환합니다.
ocp_native_job작업 상태를 조회합니다. succeeded는 최적성 증명이 아닙니다.
ocp_native_result원래 수학적 의미를 유지한 완료 도메인 결과를 가져옵니다.
ocp_native_cancel취소를 요청한 뒤 종료 상태를 확인합니다.
ocp_native_evaluate반환된 해를 평가합니다. 독립 검산은 별도입니다.

인증정보와 tenant는 도구 인자가 아니라 신뢰하는 호스트 설정에 둡니다. 응답이 불확실하면 원래 입력과 멱등 키를 유지하세요. 작업 제출·결과 수신·제공자 평가·독립 검산은 각각 별도 단계입니다. 이 로컬 binding은 전체 gateway/ocps1 state 프로파일이나 모든 모델·호스트의 수락을 주장하지 않습니다.
