Two contract layers, explicit versions

The native outer catalog/job/error uses contractVersion: "1". Reference problems declare domainPayloadFormat: "ocp-core-request/0.1.0", and JobResult.result retains the original Core result. The inner synchronous execution profile describes the solver invocation; the outer job lifecycle is asynchronous. Contract, domain-profile and package versions identify different things.

Matrix routing does not become coordinate routing, and worker assignment does not become nurse scheduling. Compare only matching domain profiles, units, costs and constraints.

Follow the job through to a checked result

  1. Discover the exact catalog and request template, resolve requirements and validate input.
  2. Submit a job; retain its job ID, input and idempotency key.
  3. Poll queued/running work to a terminal state, then fetch the result.
  4. Inspect the domain status and evaluate an available solution; run a separate independent checker.

succeeded means computation completed, not mathematical optimality. Preserve feasible/optimal/infeasible/unknown, termination, proof and unevaluated nulls. After an uncertain response, reuse the same idempotency key and input. Cancellation is a request: confirm a terminal job state before saying computation stopped. A timeout message alone is not cancellation evidence.

Compatibility and reference limits

Existing Core 0.1 imports and synchronous semantics remain supported; no removal date is set. Native clients choose explicit entrypoints and a locally built native kit. Changing a default wire format needs a versioned migration and consumer checks.

The native MCP candidate is a stateless local binding, not the full foundry-ocp-standard/v1 gateway/ocps1 state profile. Compilation, repair and ocps1 state are not advertised by these references. Localhost-only access, volatile two-hour records and a default 128-job session limit are local reference policies, not universal protocol requirements. Credentials and tenant are trusted host configuration.

Four layers

Core: capabilities, requirements, requests, validation, results, failures and evaluation. Domain/execution profiles: units, constraints, objectives and execution promises. Bindings: library, HTTP or MCP. Environment policy: identity, quota, expiry and service access.

Failure is part of the contract

Reject unsupported objectives and constraints rather than dropping them. A heuristic finding no solution is not mathematical infeasibility. Preserve unevaluated metrics as null. A separate checker detects declared violations; a passing fixture does not certify an entire engine.
