Path A: implement an existing profile

Choose this path when your engine supports an existing profile’s semantics. Declare the supported intersection, map inputs and outputs explicitly, and check returned results.

1. Run the teaching engine

Run and check your engine adapter
.agent/bin/python -B byo_library.py basic-input.json --trace own-engine-trace.json
.agent/bin/python -B export_transcript.py --trace own-engine-trace.json --artifact byo_library.py --out own-engine-transcript.json
.agent/bin/python -B -m conformance.runner --bundle own-engine-transcript.json --artifact byo_library.py

2. Replace the calculation

Replace EnumeratingLibrary.solve(problem, time_limit_ms) with your implementation. Preserve name, version and the Outcome(solution, termination, objective) result. The teaching example supports at most 6 visits and 3 vehicles. Use validation to reject unsupported behavior.

3. Declare and check meaning

Routing uses explicit integer meter distances and kg loads. Engine substitution is valid only within intersecting profiles, units, costs and constraints. Do not label a timeout infeasible or a feasible result optimal without proof. Generate a new trace after a change; existing traces are not overwritten.

Path B: define a new problem profile

For a different problem, such as production scheduling, replacing the routing solve function is not sufficient.

  1. Define a profile ID and version, input/configuration/solution schemas, units, objectives and constraints.
  2. Specify result and failure semantics, execution budgets and any proof claims.
  3. Implement capability discovery, requirements, validation, execution and evaluation.
  4. Add a separate checker, known-answer cases and counterexamples for unsupported inputs or incorrect results.
  5. Test a real application consumer and document compatibility and version changes. Until those checks exist, do not claim conformance or interchangeability.

Use the worker and inventory contracts as examples of separate domains. This is an authoring checklist; no universal profile generator is supplied.

Native v1 engine registration — local candidate

The paths above describe the public Core 0.1 kit. In the separate native candidate, a domain adapter and an importable solve function are registered with the common server. ReferenceDomain retains declared Core domain semantics, Registration(domain, solve) binds the engine, and LocalAPI supplies the shared job lifecycle. A spawned solve function must be importable; executable Python entry scripts need a main guard.

This native authoring template is part of the unpublished review materials, not this public checkout. A new problem still needs explicit schemas, semantics, supported capabilities and independent checks. Sharing a server does not make arbitrary engines interchangeable.
